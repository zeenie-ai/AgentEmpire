# Client

The client is AgentEmpire's game, a Godot 4.7.2 project in GDScript. It simulates the town (the
map, townsfolk, gathering, construction, and the agents' figures, homes and add-ons), draws it in
3D with the HUD and the agent windows, and mirrors the Town Hall's state over a local WebSocket.
Without a Town Hall it plays an offline town. How the two programs fit together is in
[../docs/architecture.md](../docs/architecture.md); this guide is about working in `client/`.

## Running it

`<godot>` is `.tools\godot\Godot_v4.7.2-stable_win64_console.exe` (`node scripts/setup.mjs`); the
`Godot_v4.7.2-stable_win64.exe` beside it has no console. A worktree uses the main checkout's
`.tools/`. Import a new checkout or worktree once: `<godot> --headless --path client --import`.

- **The editor:** `<godot> -e --path client`; Play (F5) runs `game/main.tscn`.
- **The game:** `<godot> --path client [-- options]`, with `--offline` (no Town Hall),
  `--quality=low|medium|high`, `--capture=<png>` (a screenshot two seconds in, then quit), and
  for offline towns `--age=<1..4>` or `--advance-age-after=<seconds>`.
- **A tool:** `<godot> --path client -s res://tools/<name>.gd [-- options]`.

The game reads the runtime file named by `AURELHAVEN_RUNTIME` first, then the one of the mode in
the `townhall/provider` setting, the shared copy (`AURELHAVEN_DISCOVERY_FILE`, by default
`%APPDATA%\AgentEmpire\runtime.json`; `off` skips it) and the other mode's. When none answers and
`townhall/auto_start` is on, it starts a Town Hall from `townhall/` on the data root
(`AURELHAVEN_DATA_ROOT`, else `townhall/data` in a checkout; practice towns in its `practice/`).

To play against a test Town Hall, start it on temporary data and point the game at it; the data
root keeps a Town Hall the game might start out of `townhall/data`. Ctrl+C stops the Town Hall.

```powershell
# in townhall/
$env:AURELHAVEN_DATA_DIR = "$env:TEMP\ae-hall"; $env:AURELHAVEN_PORT = "0"
$env:AURELHAVEN_DISCOVERY_FILE = "off"; npm start
# at the repository root, in another terminal
$env:AURELHAVEN_RUNTIME = "$env:TEMP\ae-hall\runtime.json"; $env:AURELHAVEN_DISCOVERY_FILE = "off"
$env:AURELHAVEN_DATA_ROOT = "$env:TEMP\ae-root"
.tools\godot\Godot_v4.7.2-stable_win64.exe --path client
```

- **The console executable waits** for every process the game started, including a Town Hall,
  which keeps running after the game quits (the Town Hall chip in the top bar closes it). Use the
  GUI executable or `-- --offline` when that matters.
- **`user://` is the player's:** editor runs, tools and the exported game all use
  `%APPDATA%\Godot\app_userdata\AgentEmpire` (settings, saves, logs), so F5 in a test run replaces
  the player's quick save. `tools/townhall_mode_check.gd` isolates it with a temporary `APPDATA`.

## Autoloads

| Autoload | Role |

They load in this order. `game/main.tscn` is a bare `Node`; `main.gd` builds the `WorldView`,
`RtsCamera`, `Selection`, `Hud` and `RtsInput` in code, then calls `Game.boot(seed)`.

## The simulation

**SimWorld** (`sim/sim_world.gd`) is plain data with no nodes: the grid, units, buildings,
resource nodes, Font Wisps, walls, the command queue and the path service; views follow its
signals. **GameCommands** (`game/game_commands.gd`) builds each command as a plain, JSON-safe
dictionary; `Game.issue(cmd)` queues it, and **CommandApplier** (`sim/commands/`) applies it at
the start of the next tick or drops it when invalid, with a notice if the player should know.

**The clock.** `Game._process` feeds real elapsed time (at most 1 s a frame) into an accumulator
and steps the world at `economy.json`'s `tick_rate`, 20 a second, at most 64 ticks a frame;
`Game.interp_alpha` says how far views are between ticks. Tests call `w.step(n)`. Each tick:

1. applies the queued commands and records them (`commands.history` keeps the last 4096);
2. serves queued path requests;
3. stores each unit's `prev_pos` for interpolation;
4. runs the systems in `sim/systems/`: units (their jobs from `sim/jobs/`, which keep their state
   on the `SimUnit`, path following, steering), construction, training, regrowth, wisps, wanderers;
5. counts the tick and emits `ticked`.

**Path finding.** `SimGrid` holds each cell's terrain and occupant and an `AStarGrid2D` over the
128 x 128 map; rocks, live trees and bushes, standing walls and buildings (not fields) are solid.
`Pathing` runs A*, where a partial path means "can't reach". `PathService` serves queued requests
for up to 2.5 ms a tick (one to 48), or a fixed number with `deterministic = true`, as in tests.
`Placement` checks footprints, `HomeLayout` lays out agent plots and `WallLayout` the walls.

**Saves.** `SimSerializer` (`sim/save/`) turns a world into a JSON-safe dictionary with
`schema_version` (`SimConst.SCHEMA_VERSION`, 3 today) and back, refusing a newer schema and
upgrading an older one. Written with `JSON.stringify(doc, "", true, true)` (sorted keys, full
float precision), a loaded town steps exactly like the saved one.

| | Offline quick save | The Town Hall's town |
|---|---|---|
| When | F5 saves, F9 loads (`Game.save_offline()`, `Game.load_offline()`) | `TownLink.save_now()`: every 60 s; 2 s after a new town opens, an agent is summoned, a home is placed, or a home or add-on is finished; on quit (waiting up to 2 s); before the Town Hall is switched or closed; on F5 |
| Where | `user://saves/quick.json` | The Town Hall (`save_town`, `load_town`), which stores it as given |
| Format | JSON: `{"format": "aurelhaven-offline", "sim", "ledger"}` | `{"encoding": "json+gzip+base64", "bytes", "data"}` around `{"sim", "ledger", "client"}`, sent with `base_rev`; a stale `base_rev` gets `CONFLICT` |

**Only GameCommands change a SimWorld.** Views, the HUD and input only read it, and TownLink
mirrors the Town Hall with commands too. Commands land on tick boundaries, are plain data that can
be logged and saved, and spend through `w.ledger`, which keeps the treasury in step with the Town
Hall's ledger; TownLink's agent commands are idempotent, so catching up after a reconnect is
harmless. Replays and shared towns on the command log are planned, not built. Selection, the
camera and hover are view state; `debug_spawn` and `debug_set_age` need `allow_debug_commands`.

## Talking to the Town Hall

- **Net** (`autoload/net.gd`) owns the WebSocket: discovery, `hello`, reconnects and catch-up
  ([architecture.md](../docs/architecture.md#the-protocol), with every message in
  [PROTOCOL.md](../protocol/PROTOCOL.md)); a second client waits until `Net.take_over()`.
- **NetRequest:** `Net.request(type, payload)` returns one; await `req.done`, then read `req.ok`,
  `req.payload_dict()` or `req.error_message()`, a sentence for the player. `done` always fires
  on a later frame, also for `OFFLINE` and `TIMEOUT` (after 30 s).
- **Realm** (`autoload/realm.gd`) holds the Town Hall's objects as protocol dictionaries:
  `apply_state()` replaces them all (`reset`), `apply_event()` one. Listen to `changed(kind, id)`
  or a signal such as `task_changed(task, previous_state)`; query with `tasks_of()` and the rest.
- **TownLink** (`game/town_link.gd`, `Game.link`) mirrors Realm into the town through
  GameCommands and offers the player's actions (`summon()`, `assign_task()`, `respond_approval()`,
  `accept_result()`, ...); `is_live()` says whether they are possible. Its `RemoteLedger` sends
  each spend, refund and gather batch with its operation id as the request id; a spend the Town
  Hall refuses is undone with `revoke_spend`.
- **`net/protocol.gd`** holds every message type, error code and enum, generated from the zod
  schemas (`cd townhall; npm run gen:gd`) and copied by `node scripts/sync-economy.mjs`: never
  edit it. It has no class name: `const Protocol = preload("res://net/protocol.gd")`.
- **J** (`net/j.gd`) reads protocol values safely, as optional fields arrive as null and numbers
  as floats: `J.gs(obj, "key")`, `J.gi()`, `J.gd()`, and `J.s()`, `J.i()`, `J.a()` and the rest.

## World and UI

**Views.** `WorldView` (`world/world_view.gd`) binds to a `SimWorld` and keeps a view per unit
and building (trees and bushes are MultiMesh slots). Every frame `UnitView` places each unit
between `prev_pos` and `pos` at `Game.interp_alpha`; views never write to the world. `RtsCamera`
(`world/camera/`) sees the world through the space between the top bar and the bottom panel.

**UI in code.** There are no UI scenes: every control is built in GDScript.

- **The theme:** `ThemeBuilder.theme()` (`ui/theme/`) builds it from `UiTokens` (the handoff's
  colours and metrics) and `UiFonts`, with type variations such as `HudPanel`, `DocumentPanel`,
  `TitleLabel` and `CardButton`. `CraftedBox` is the `StyleBox` behind panels, buttons and toasts,
  drawn in code: shadow, wood grain, bevel, gold trim and studs.
- **Windows:** `WindowFrame` (`ui/agents/`) is the shared frame (`head`, a scrolling `body`, an
  optional `side`, `tray`, `footer`) in an `AgentTheme` look, `DOCUMENT` (parchment) or `STATUS`
  (navy). It stays inside the viewport, and Esc closes the topmost one.
- **The HUD:** `Hud` (`ui/hud/hud.gd`) holds the top bar, the bottom panel (minimap, selection,
  command card), toasts, the approval tray, the task tracker and the window stack:
  `open_window(w)` dims the town and puts `w` on top, and `confirm(title, text, on_yes)` asks a
  Yes or No question. `RtsInput` ignores the world while a window is open. `TaskTracker`
  (`ui/hud/task_tracker.gd`) lists the live tasks top left under the top bar, the ones that need
  the player first (`ORDER`), at most five rows; a task that just ended stays on top with its
  final seal for six seconds. It follows Realm's signals and asks the HUD for the review, the
  petitions or the agent (`review_requested`, `approvals_requested`, `focus_requested`). The HUD
  turns it off (`enabled`) on phones and tablets, which have no Town Hall
  (`Platform.has_town_hall()`), and in the phone layout. It shows only while the town is the Town
  Hall's (`Game.is_online_town()`; tests set `online`), and hides itself while nothing is tracked.
- **The Rive state tracker:** the task seals and agent sigils are drawn in RML in
  `art_src/rive/state_tracker/` and baked by `scripts/bake-rive.mjs` into one sprite sheet per
  state, `art/rive/<set>/<state>.png`, described by `art/rive/rive_sprites.json`
  ([Art](../docs/development.md#art)). The game has no Rive runtime.
  - `RiveSprites` (`ui/widgets/rive_sprites.gd`) reads the manifest and loads a state's sheet the
    first time it shows. A state without a sheet shows the set's fallback (`queued`, `idle`).
  - `RiveSprite` (`ui/widgets/rive_sprite.gd`) is the control that plays one:
    `RiveSprite.new(set, state, px)`, then `set_state()` crossfades into the new state over the
    set's blend time (200 ms), with a small pop. A state that was never drawn does not fade out:
    the first state after the sprite was made just appears. It animates only while visible.
  - `TaskTracker` uses the `task_seal` set; `AgentPanel` and `NamePlate` use the `agent_sigil`
    set, and `HomeStatusView.plate_mood()` picks a plate's mood.

**Fonts.** Four OFL families in `ui/fonts/<family>/`, each with its `OFL.txt`: Cinzel for titles
and buttons, Cormorant for display text, Spectral for body text (the default, 16 px) and
JetBrains Mono for labels and numbers. `UiFonts` caches a `FontVariation` per weight.

**Screen size.** The base size is 1600x900 with the `canvas_items` stretch mode and the `expand`
aspect: the UI is laid out at 1600x900 and scaled to the window, while the 3D world renders at the
window's resolution. At 1280x720 the UI is drawn at 0.8 of its size, so check that small text
stays readable; at 2560x1440 and 3840x2160 it is 1.6 and 2.4 times as large. Other aspect ratios
give the UI more room one way, so anchor controls to edges. There is no UI-scale setting. Desktop
builds render with Forward+, the web with the Compatibility renderer, for which `GraphicsQuality`
leaves out SSAO, SSIL, volumetric fog, depth of field and decals.

## Input

- **InputActions** (`input/input_actions.gd`) lists every rebindable action with its default
  physical key, so the card keeps its shape on any layout: `card_0` to `card_14` (Q W E R T,
  A S D F G, Z X C V B), `group_1` to `group_9` and the rest. `Settings` registers them at start
  and applies the saved `[keybinds]`; Ctrl and Alt variants are resolved in code.
- **RtsInput** (`input/rts_input.gd`) turns mouse and keys in the world into selections, orders
  and the placement and rally modes, through `Game.issue()` or, when the Town Hall must agree
  first (a plot, an add-on, a task), through TownLink.
- **RightClickRules** (`input/right_click_rules.gd`) is a pure table from the selection, the
  target and whether a unit carries what the target accepts to an action (`move`, `gather`,
  `build`, `deposit`, `rally`, `deliver`); `command_for()` builds the command.
- **The command card model:** `CommandCardModel.slots(world, selection)` returns 15 slots as
  plain data (`id`, `label`, `icon`, `tooltip`, `cost`, `enabled`, `active`). A click on
  `CommandCard` and a hotkey both end in `RtsInput.activate(slot)`, which acts on the slot's `id`.
- **Camera controls** live in `RtsCamera`: the arrow keys, the screen edge and middle-drag pan;
  the wheel zooms toward the cursor (10 to 70 tiles); Ctrl+Left and Ctrl+Right rotate in
  45-degree steps, Alt+middle-drag freely.

## Settings

`Settings.get_value(key)` and `set_value(key, value)` use `user://settings.cfg`; `set_value()`
saves at once and emits `changed`. `Settings` loads only the keys in `Settings.DEFAULTS`, so a new
key goes there first, or it is forgotten at the next start. The `[keybinds]` section maps actions
to physical key codes.

| Key | Default | Read by | UI today |
|---|---|---|---|
| `camera/edge_scroll`, `camera/pan_speed` | `true`, `1.0` | `RtsCamera`, when it starts | None |
| `display/show_fps` | `false` | `Hud` | F3 |
| `graphics/quality` | `""`: High on desktop, Low on the web | `GraphicsQuality`, live | None; `-- --quality=` overrides it |
| `audio/master`, `audio/music`, `audio/sfx`, `audio/ui`, `audio/ambience` | `0.8`, `0.6`, `0.9`, `0.8`, `0.6` | `Audio`, live | None |
| `audio/mute_unfocused` | `true` | `Audio`: quiet while the window is in the background | None |
| `game/seed` | `4127` | The map of a new town | None |
| `townhall/auto_start` | `true` | `Game.boot()`: start a Town Hall when none runs | None |
| `townhall/provider` | `"fake"` | The mode to look for and start: `fake` (practice) or `real` | The Town Hall chip's menu |
| `onboarding/done`, `onboarding/work_folder` | `false`, `""` | Nothing yet | None |
| `onboarding/touch_help` | `false` | `HelpPanel`, when a phone or tablet starts: the touch help opens once, then this turns `true` | None; the game menu's How to play shows the help again |
| `hud/tracker_folded` | `false` | `TaskTracker`: only its header shows | A click on the task tracker's header |
| `[keybinds]` | empty | `Settings`, at start | None |

There is no settings window yet: the menus and the onboarding are still to come.

## How to

### Add a GameCommand

1. Add a constant and a static constructor returning plain values to `game/game_commands.gd`.
2. Add a branch to `CommandApplier.apply()` and a `_<name>(w, cmd)` that reads fields with
   `int()` or `String()` (JSON numbers are floats), drops an invalid command (with
   `w.emit_notice()` if the player should know) and spends with
   `w.ledger.spend(w.next_op_id(kind), ...)`. Keep agent commands idempotent.
3. Issue it with `Game.issue()` from `RtsInput` or `TownLink`. New world state goes into
   `SimSerializer`; raise `SimConst.SCHEMA_VERSION` when the layout changes.
4. Test it (push, `w.step(1)`, check) and add it to `tests/unit/test_commands.gd`.

### Add a window

1. Subclass `WindowFrame`: in `_init()`, call `super()` and `configure(title, subtitle, look,
   width)` with an `AgentTheme` look, fill `head`, `body`, `side` or `tray`, and add footer
   buttons with `add_button(text, kind)`.
2. Connect to Realm in `_window_opened()` with `listen()`, which disconnects on close; act through
   `the_link()` and query with `request()`, which tests replace with fakes.
3. Open it from an `open_<name>()` in `Hud` with `open_window()`, after `_needs_town_hall()` if it
   needs the Town Hall. Add a shot to `tools/ui_preview.gd` and a test to
   `tests/unit/test_agent_ui.gd`, and look at it at 1280x720 and at a large size.

### Add a sound cue

1. Add a recipe to `scripts/fetch-audio.mjs` (`cue(name, group, fmt, build)`, with one of the
   existing `audio/` folders as `group`, and `WORLD` for a cue in the world), then run
   `node scripts/fetch-audio.mjs --only <name>` (needs ffmpeg): it writes the files and
   regenerates `audio/cue_files.gd`.
2. Add the name to `CANONICAL` and its mix to `CUES` in `audio/cue_table.gd`, and raise the cue
   count in `tests/unit/test_audio.gd`.
3. Play it with `Audio.play(cue)` or `Audio.play_at(cue, position)`, and check its loudness with
   `tools/audio_check.gd -- --only=<name>`. Buttons and windows sound by themselves (the meta
   `audio_silent` keeps a control quiet).

### Add a model or building

1. A building type goes into `buildings` in `protocol/economy.json` (`footprint`, `built_by`,
   `cost`, `build_s`, `age`, and `pop`, `dropoff` or `role`); run the sync script. Townsfolk
   show up to five buildings in their card's top row.
2. Add the model to `art_src/manifest.json`, rebuild the art ([Art](../docs/development.md#art))
   into `art/models/<id>.glb` and `art/icons/<id>.png`, and map `building/<type>` to that id in
   `AssetCatalog.MODEL_IDS`. Without a GLB, `ModelLibrary` has procedural stand-ins only for the
   Keep, Cottage, Farm and Storehouse; anything else shows a magenta box and a warning.
3. Look at it in a town (`tools/capture_screens.gd`) and test its placement and construction.

### Change a task seal or agent sigil

1. Edit the RML in `art_src/rive/state_tracker/` and check it with
   `rive art_src/rive/state_tracker --verify`; `rive art_src/rive/state_tracker` opens a preview
   that rebuilds on every save. A new state needs three things in the RML: a `DataEnumValue` in
   `data.rml` whose key is the state's name; a looping `LinearAnimation` of the same name, a whole
   number of 30 fps frames long; and an `AnimationState` that plays it, with a transition to it
   from the `AnyState` of the artboard's `Tracker` state machine.
2. Bake with `node scripts/bake-rive.mjs` (about five minutes), then import the client.
   `--only=task_seal:<state>` gives a quick look, but `--check` then still asks for a full bake.
3. For a new state, add it in the client. A task state (a
   [protocol change](../docs/development.md#changing-the-protocol) first) goes into
   `TaskTracker.ORDER` and `TaskTracker.state_color()`; a mood into `AgentUi.agent_status()`,
   `HomeStatusView.plate_mood()` for the name plates and `MOODS` in
   `tests/unit/test_rive_tracker.gd`. A state without a sheet shows the set's fallback.
4. Look at the `rive_states` and `task_tracker` shots of `tools/ui_preview.gd` at 1280x720 and at
   a large size. Commit the RML, the sheets with their `.import` files and `rive_sprites.json`
   together.

### React to a new Town Hall event

1. Add it to the protocol ([Changing the protocol](../docs/development.md#changing-the-protocol)).
2. Handle `Protocol.EVT_<NAME>` in `Realm.apply_event()`: replace the stored object and emit
   `changed(kind, id)` or a new signal. If `get_state` carries the object, read it in
   `apply_state()` too: a reconnect can bring a full state instead of the events.
3. React in TownLink (through GameCommands), the HUD, a window or `Audio`, and test it by feeding
   Realm the event, as `tests/unit/test_townhall_progress.gd` does.

## Tests

GUT 9.7.1 (`addons/gut/`) runs every `tests/unit/test_*.gd` (39 files, 407 tests today) with the
defaults in `.gutconfig.json`. The autoloads exist in tests, but no test starts a Town Hall.

| Run | Command, from the repository root |
|---|---|
| Every test | `<godot> --headless --path client -s addons/gut/gut_cmdln.gd -gdir=res://tests/unit -gexit` |
| One file | The same with `-gselect=test_walls.gd` (part of a file name) |
| Some tests | The same with `-gunit_test_name=<part of a test name>` |

GUT exits with 1 when a test fails. `SimFixture` (`tests/fixtures/sim_fixture.gd`) builds worlds
with a deterministic path service, `empty_world()` (only the Keep) or `generated_world(seed)`;
tests step them with `w.step(SimFixture.ticks(w, seconds))`, so they take no real time.

The tests cover the simulation, the economy data and both ledgers, the right-click table, finding
a Town Hall, Realm's progress, the agent windows against a fake TownLink, the audio, the Town Hall
chip, the camera's framing, the walls in a `WorldView`, and the Rive state tracker (the baked
sheets against their manifest, `RiveSprite`, the HUD's task tracker and the agent sigils). They
leave out a real Town Hall, input through `RtsInput`, the command card model, most of the HUD and
how anything looks. These tools check part of that:

| Tool | Checks |
|---|---|
| `e2e_client.gd` | The whole loop against a real Town Hall with the scripted agent, headless; run it with `node scripts/e2e-client.mjs`, which gives it an isolated Town Hall (the game itself still uses the normal user folder) |
| `input_smoke.gd` | Injected mouse and keys: box select, gather, place a Cottage, train, rally, and a control group with Esc between; needs a real window |
| `boot_check.gd` | Boots like a player, headless, and reports which town it reached and how fast. With no Town Hall it starts one on the data root that keeps running: set `AURELHAVEN_DATA_ROOT` to a temporary folder and `AURELHAVEN_DISCOVERY_FILE=off` first, and stop it afterwards |

## Conventions

The [GDScript rules](../docs/development.md#gdscript-conventions-and-pitfalls) apply. Also:

- **Every script says what it is:** a `class_name` (except autoloads, tools, tests and the
  preloaded `protocol.gd`, `cue_table.gd`, `cue_files.gd`) and a `##` comment at the top.
- **Numbers come from `EconomyData`** (`Economy.data`, `w.econ`), client-only tuning from
  `SimConst`. One exception today: `HomeLayout` repeats the 7 x 7 plot and the 3 x 3 home.
- **Simulation units:** tiles for positions (`Vector2` x and y are the world's x and z), ticks for
  time, thousandths for resources (`amount_m`, `carry_m`), `SimConst.WORK_SCALE` parts for
  construction. In 3D, +Y is up, one unit is one tile and models face +Z.
- **Tests leave the player alone:** no `user://` writes, no Town Hall, fakes for autoloads (as in
  `test_audio.gd` and `test_agent_ui.gd`), and environment variables restored after use.
- **Messages:** `Notify.push()` for the player, `ClientLog` for the log, `print()` only in tools;
  British English and no emojis.
